# Ophir 资源与驱动同步修复设计

## 背景

功率计识别接口返回供界面显示的标签，例如：

```text
Ophir USB | OPHIR::USB::3103403 | USB SN 3103403
```

当前前端仅在字符串以 `OPHIR::USB::` 开头时才把它视为 Ophir 资源，因此会把整段显示标签保存为资源值。同时，异步识别线程更新资源与驱动类型后没有立即持久化；应用重启后可能形成“完整 Ophir 标签 + `caihuang` 驱动”的不一致配置。启动功率采集时，后端据此选择彩煌 PyVISA 驱动，并把无效显示标签传入 `open_resource`，最终触发 `VI_ERROR_RSRC_NFOUND`。

## 目标

- 将任何包含 `OPHIR::USB::<序列号>` 的显示标签规范化为稳定资源标识。
- 保证 Ophir 资源始终与 `ophir` 驱动类型同步。
- 自动迁移已经保存的不一致 Ophir 配置。
- 异步设备识别成功后立即持久化选择结果。
- 保持彩煌、Coherent、LaserPoint 串口识别和双工位配置行为不变。

## 方案

### 前端资源规范化

把功率计资源解析提取为可单独测试的纯函数。解析规则为：

1. 在输入任意位置查找 `OPHIR::USB::` 资源标识，找到后返回规范化标识。
2. 否则查找 `ASRL<n>::INSTR`，找到后返回标准大写形式。
3. 均未找到时返回去除首尾空白的原字符串，兼容尚未识别的历史值。

下拉列表的 `value` 继续只保存稳定资源标识，显示文本仍使用设备识别返回的友好标签。

### 后端配置同步与迁移

在后端增加统一的功率计配置规范化边界：

- 从显示标签或原始值中提取稳定资源标识。
- 资源以 `OPHIR::USB::` 开头时，强制驱动类型为 `ophir`。
- 非 Ophir 资源不盲目覆盖已识别的 `coherent`、`laserpoint` 或 `caihuang` 类型。

该规范化在两个入口执行：

1. `StationRuntime` 加载保存配置时，用于迁移现有错误数据。
2. `StationRuntime.configure` 接收前端资源变更时，用于保证运行期一致性。

这样即使旧版前端、缓存数据或外部调用传入完整 Ophir 标签，后端也不会再选择 PyVISA 串口驱动。

### 异步识别持久化

功率计识别线程的 `detected` 回调选中设备并同时更新资源与驱动类型后，立即调用统一配置持久化方法。持久化必须发生在资源和驱动两个字段都写入以后，确保磁盘上不会出现半更新状态。

若识别结果为空，不修改也不持久化当前选择。

## 数据流

```text
识别结果友好标签
  -> 前端提取稳定资源值
  -> app.configure
  -> 后端再次规范化并同步驱动类型
  -> 运行期配置
  -> settings.json

异步识别结果
  -> 后端选择 PowerMeterOption
  -> 同时写入 resource + driver_kind
  -> 立即持久化
```

## 错误处理

- Ophir 标签无法提取稳定标识时保留原值，后续设备识别仍可纠正，不静默清空用户选择。
- 只根据明确的 `OPHIR::USB::` 标识推断 `ophir`，避免误判普通串口设备。
- 持久化沿用现有 `JsonSettings` 原子写入行为。

## 测试

- TypeScript 单元测试验证 Ophir 显示标签、原始 Ophir 标识、ASRL 标签和未知值的解析。
- Python 单元测试验证旧 Ophir 配置在加载时被迁移为规范资源和 `ophir` 驱动。
- Python 单元测试验证运行期配置变更同步驱动类型。
- Python 单元测试验证异步识别成功后资源与驱动一起写入持久化存储。
- 运行相关前端测试、后端测试及类型检查，确认现有串口功率计行为不回归。

## 非目标

- 不修改 Ophir COM API 或功率读取协议。
- 不重构设备资源协议为结构化对象。
- 不自动安装或修复 Windows/VISA/Ophir 驱动。
- 不处理当前物理设备未连接的问题。
