# 实时采集和自动测试耗时定位

测量日期：2026-10-15。基准提交：`9ca676a9fbe3c008e1b1feff54a06fb693c46d1a`。

本机软件侧最大的持续计算开销是光谱分析，其中 SMSR 是最大的单项。自动测试的墙钟时间主要消耗在原有判稳、稳定保持和电源安全等待。当前负载下，快照锁、Rust 通信处理和 Canvas 绘图没有表现出需要优先重构的阻塞。

这些结论适用于下面的模拟设备、本机磁盘和浏览器负载。真实仪器读取、积分、串口、USB、OceanDirect DLL 和 Windows WebView2 未测量，不能据此判断它们的耗时。没有为了计时缩短产品采集间隔、判稳窗口、稳定保持、重试或安全命令间隔。

## 测的是什么

- 本机 Apple Silicon/macOS、Python 3.11.15、已实际加载 ABI 2 的 `libarp_realtime_core.dylib`。Python 产品源码在测量前后核对 SHA-256，共 42 个文件。
- 真实 `PowerMeterReaderThread.run()`、`SpectrometerReaderThread.run()`、采集回调、光谱分析、`SnapshotBuilder` 和当前生产 `encode_response()`；只把仪器端口替换为确定性模拟对象。模拟端口不会扫描或打开仪器。
- 使用默认 100 ms 功率计/光谱仪间隔、固定积分模式、单帧平均；独立计算基准另覆盖 3648/8192 点和 1/5 帧滚动平均。所有光谱包含主峰和可分辨旁峰，实际执行 SMSR 和峰值标注。
- 自动测试使用标准脚本的两点计划 2 A → 4 A。执行实际 `_run_automatic_point()`、安全下电、会话完成和 Excel 保存路径；不包含真实仪器启动、识别、故障重试与许可证流程。初始命令槽设为刚被占用，用于覆盖真实 1.1 秒等待门槛。没有替换时钟或等待函数。
- 测试记录位于临时目录，实际执行逐点 JSONL 写入、`os.fsync()`、数据库归档及后台 Excel 导出；未改动用户记录。临时工作簿完成后核对保存点数、每点光谱长度和文件存在性。
- 浏览器使用该提交的独立源码副本、独立 Vite 缓存及端口 1422。另一路工作正在修改主工作区前端，因此没有用混合源码进行前端计时，也没有改动那一路的文件。副本除诊断服务器配置外的文件哈希保持一致。
- 实际应用和生产 React 运行时，1440×900，1200 个功率历史点，3648/8192 个完整光谱点。每次接收都执行生产快照校验、数据合并、状态更新及真实图表绘制。场景为 3648 点正常 CPU、8192 点正常 CPU、8192 点 4 倍 CPU 降速，各 3 组，每组 40 帧，共 360 帧。

计时以 `perf_counter_ns()` / `performance.now()` 为准。Python 记录同线程嵌套区间，`wall` 包括子调用和等待，`exclusive` 仅扣除同线程已记录子调用；跨线程和不同输入的独立数字不能直接相加为整条链路延迟。中位数和 P95 是对应样本分布，不是设备或操作系统的保证。

## 实时采集：计算开销在光谱分析

以下为 8192 点、单帧平均的独立分析复测，每种计时开关交错执行 100 次。预热后检查完整 `SpectrumFrame` 等值，包括全量数组、统计、PIB、SMSR、饱和结果和峰值标注。

| 软件环节 | 中位耗时 |
| --- | ---: |
| 完整平均、分析和发布 | 5.94 ms |
| SMSR | 1.78 ms |
| 光谱统计：峰值、中心、半高宽等 | 1.06 ms |
| 峰值标注 | 0.97 ms |
| 滚动平均及输入数组转换 | 0.75 ms |
| PIB | 0.68 ms |
| 单次饱和检测，每帧调用两次 | 0.24 ms |
| 复制到最新帧邮箱 | 0.046 ms |

初次独立测量的完整分析中位数为 7.07 ms，两次复测约为 6.07 / 5.94 ms。最后一次复测中，记录关闭/开启的整次调用中位数为 5.931 / 5.946 ms，记录增量约 0.015 ms；前一次增量约 0.046 ms。不能把时间戳记录开销解释成数毫秒到十几毫秒的分析耗时。

同时运行两个真实采集线程、快照构建/编码以及自动测试时，第一份墙钟报告的完整分析中位数为 19.29 ms，P95 为 22.11 ms；SMSR 为 5.22 ms，统计为 3.83 ms，平均为 3.08 ms。此数包含线程调度和并发干扰，不能直接解释为纯 CPU 执行时间；本机不同运行的负载和调度差异很明显，因此保留独立和并发结果，不挑一个值当作普遍性能。

追加一轮两点墙钟复测后，完整分析中位数为 8.08 ms、P95 为 20.52 ms，SMSR 为 2.40 ms；快照构建为 0.39 ms，生产 JSON 编码为 1.15 ms。相对排序不变，但并发中位数确实存在明显波动。因此软件侧的判断是“光谱分析是相对热点”，并未证明有稳定的几十毫秒阻塞，更不能将一次运行的 19.29 ms 当作固定成本。

第一份墙钟报告共收到 630 个功率读数和 520 帧光谱。功率发布间隔中位数为 99.98 ms、P95 为 104.80 ms；光谱为 123.20 ms、P95 为 127.45 ms。光谱线程保持原来的“读取、分析、发布后再等待 100 ms”节奏，所以实际发布周期包含处理时间。模拟光谱读取只是复制预制数组，不包含真实积分或 USB 时间。上述周期不是降低采集频率得到的结果，也不代表真实仪器能达到同一周期。

追加复测中，功率发布间隔中位数为 100.01 ms，光谱为 112.54 ms。新工具的快照游标只从实际收到的响应更新，避免把构建响应后才到达的功率点误当作已接收；这与生产 Rust 流的游标规则一致。该修正在诊断工具中，产品代码未修改。

### 快照和通信

| 场景和范围 | 中位耗时 | P95 |
| --- | ---: | ---: |
| 并发运行中的 Python 快照构建 | 1.16 ms | 2.31 ms |
| 同一并发运行中的当前生产 JSON 编码 | 2.65 ms | 4.01 ms |
| 独立 Rust 8192 点增量响应解析 | 0.126 ms | 0.143 ms |
| 独立 Rust JSON 编码 | 0.090 ms | 0.104 ms |
| 独立 Rust UTF-16 转换 | 0.045 ms | 0.055 ms |
| 独立 Python 队列、OS 管道至 Rust 消息编码，8192 点增量 | 1.02 ms | 1.09 ms |

最后一项使用实际生产 Rust 响应线程和 600 帧既有管道回归。为隔离处理时间，该独立基准不执行流循环等待，只检查传入等待函数的原有 100/500 ms 参数；它不用于证明实际刷新周期。前面的墙钟采集及自动点测试均保留真实等待。两者输入、并发条件和测量边界不同，不能相加或直接比较快慢。

既有快照基准也重新运行了 3648/8192 点和五种响应。8192 点静态构建中位数约 0.26 ms，状态锁探针最大等待约 0.03 ms。该工具的 `json_encode` 字段使用标准库参考编码器，不能当作当前生产编码器的数据；上表的当前生产编码来自本轮新工具。

### 浏览器没有出现持续掉帧

下表取三组中位数的中位数；P95 列取三组中最高值。单位均为 ms。

| 场景 | JSON 解析 | 校验 | 快照合并 | 功率底图 | 光谱底图 | 接收至两张底图绘图指令完成 | 该延迟 P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3648 点、正常 CPU | 0.4 | 0.1 | 0.1 | 0.3 | 0.2 | 12.9 | 21.8 |
| 8192 点、正常 CPU | 0.3 | 0.1 | <0.1 | 0.2 | 0.2 | 12.0 | 20.5 |
| 8192 点、4 倍 CPU 降速 | 1.0 | 0.4 | <0.1 | 0.5 | 0.8 | 15.4 | 24.8 |

浏览器计时精度约 0.1 ms，显示为 0 的合并中位数不能理解为没有成本。实际输入间隔的组间中位数为约 101.1 / 101.1 / 101.4 ms。每组 40 次更新均完成两张底图各 40 次绘制；360 帧逐帧核对 1200 个功率历史点和完整光谱点数。rAF 帧间隔 P95 不超过 16.8 ms，未记录到大于 34 ms 的间隔，页面脚本异常为 0。

“接收至绘图指令完成”包含 React 更新、effect 和 rAF 等待，不能全部归因于绘图。它不包含 Python、原生 WebView 消息投递、GPU 实际呈现或屏幕显示延迟。浏览器 Vite HMR WebSocket 被本地网络策略拦截的控制台消息不属于页面脚本异常。

## 自动测试：88% 时间用于判稳和稳定保持

两轮各保存 2 个测试点、每点完整 8192 点光谱，包含安全下电和 Excel 保存。总耗时分别为 **28.951 / 28.957 秒**。

| 环节 | 实际墙钟耗时 |
| --- | ---: |
| 每点设电流，包含原有安全槽等待 | 1.069–1.105 s |
| 每点最初判稳 | 5.118–5.211 s |
| 第一测试点稳定保持 | 5.082–5.093 s |
| 最后测试点稳定保持 | 10.062–10.083 s |
| 每点记录提交，包含转换、JSON、写入和 fsync | 16.35–32.96 ms |
| 单次 fsync，含会话/保存事件共 12 次 | 中位 0.083 ms，最大 0.359 ms |
| 完成后的安全下电 | 1.076–1.083 s |
| 整份 2 点工作簿保存 | 95.91–105.66 ms |

两轮判稳和稳定保持合计占总耗时 **88.1%**；电源命令安全等待及下电再占约 11.3%。读电压端口为模拟对象，其调用时间不能当作真实设备时间。单次 fsync 数值仅代表本机临时目录上的实际 `os.fsync()` 调用；不等于 Windows 磁盘延迟，也没有额外添加更强的磁盘刷新语义。

追加一轮复测总耗时 **28.939 秒**，判稳及稳定保持仍占约 **88.1%**。该轮两个点提交为 15.49 / 19.18 ms，后台实际工作簿写入 85.26 ms，包含等待与标记保存的总调用 85.54 ms；这两个跨线程区间相互重叠，不能相加。记录的相邻电流/读压命令实际最短间隔为 **1101.28 ms**，原有 1.1 秒限制保持。三轮共保存 6 个点，每点完整 8192 个光谱样本。

稳定输入下仍可看到约 0.1–0.2 秒的采样、判稳轮询和下一帧对齐开销。这不同于计算卡住；在保持当前采样和确认规则的前提下，不能把完整 5/10 秒当作可删除的等待。

### 保存开销主要不在 fsync

另从真实 `SessionRecordStore.queue()` 捕获一份 8192 点提交事件，保留实际写盘，并验证分段重新编码与实际日志最后一行逐字节相同。对同一事件各执行 100 次 CPU 分段计时：

| 环节 | 中位耗时 |
| --- | ---: |
| dataclass 深复制及递归 JSON 值转换 | 11.77 ms |
| 已转换对象的 JSON 编码及 UTF-8 | 2.38 ms |

此样本约 200 kB。分段使用同一捕获事件，没有重新生成 UUID 和时间；它用于定位保存的 CPU 成本，不能与并发点提交的中位数拼接成同一次保存。它说明后续若优化保存，应先检查数据转换，不应通过取消逐点 fsync 换取速度。不过每点只发生一次，优先级低于持续执行的光谱分析。

## 接下来值得改什么

1. **先检查光谱分析的重复转换和遍历。** SMSR、统计、标注、平均和 PIB 共用同一组数组；持续计算成本高于本次测得的消息处理和绘图。可先建立相同输入下的前后等值比较，再决定是否复用内部计算。需要覆盖多峰、噪声、饱和、不规则波长网格和边界输入，不能改变公式或丢弃采样点。
2. **记录转换可以作为次级优化。** 有可测的 dataclass/JSON 转换成本，但对当前每点十几秒的自动测试影响很小，不宜把它包装成整轮显著加速。
3. **暂不重写通信、状态锁或图表。** 当前证据没有显示这些部分是该负载下的主要持续瓶颈。二进制协议、跨线程绘图等方案会增加维护和精度验证成本，现有收益依据不足。

如果目标是减少真实 Windows 测试时间，尚缺同一台目标机上真实功率计读取、光谱仪积分/读取、读压及 fsync 的分段分布。当前设备读取都使用模拟端口，不能为这些未知量填入猜测值。本轮没有实施上述性能优化。
