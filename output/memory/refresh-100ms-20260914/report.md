# 100 ms 实时图内存排查（2026-09-14）

## 修改

保留 `LIVE_SNAPSHOT_INTERVAL_MS = 100`。有序、无重叠的历史增量改为直接裁剪并追加引用，避免每次更新重建全部历史点的 Map、键值对数组和排序结果。乱序、重复、重叠更新仍走原来的合并逻辑；历史点、原始测量值和硬件采样方式不变。

实现：`tauri-ui/src/lib/snapshot-series.ts`。8 个针对性测试通过，覆盖重复时间戳、乱序、重置后的旧响应、滚动窗口及不修改原数组。前端构建通过。

## 合并环节基准

同一 Node 运行环境，1200 点滚动历史、20000 次增量合并，使用分配采样（包含被回收对象）。

| 指标 | 原实现 | 优化后 |
| --- | ---: | ---: |
| 总耗时 | 2220.3 ms | 93.1 ms |
| 累计采样分配量 | 7563.1 MiB | 193.5 MiB |
| 最终历史点数 | 1200 | 1200 |

该环节累计临时分配减少约 97.4%，耗时减少约 95.8%。这是合并环节的基准，不能解释为软件总内存减少 97%。详见 `baseline-bench.json`、`candidate-bench.json`。

## 验证边界

完成一次有效的 300 秒浏览器整页对比：同一 Vite 生产 React 运行时，1440×960 CSS 像素、DPR 1.5；每 100 ms 更新 1200 点滚动功率历史和 2048 点光谱。原实现与优化后各使用独立页面，强制页面可见并隔离开发热重载。此前受到后台节流或热重载影响的两轮不纳入结论。

| 指标 | 原实现 | 优化后 |
| --- | ---: | ---: |
| 实测更新频率 | 10.001 Hz | 9.998 Hz |
| 采样 JS 堆范围 | 11.75–33.88 MiB | 9.90–36.92 MiB |
| 结束强制回收后 JS 堆 | 10.956 MiB | 10.961 MiB |
| 脚本累计执行时间 | 7.107 s | 6.703 s |
| 页面错误 | 0 | 0 |

每组每 15 秒采样一次，共 20 次自然运行采样，结束时另执行一次 GC。历史点数始终 1200、Canvas 始终 6、文档始终 1；DOM 在初始化后保持 655。页面截图确认曲线正常显示。详细记录为 `ui-comparison.json`，截图为 `ui-baseline.png` 和 `ui-optimized.png`。

这次整页对比没有证实 JS 保留内存或峰值下降：两组回收后内存几乎相同，优化后的采样峰值甚至略高。单次脚本累计耗时约减少 5.7%，这里只作为辅助证据，不能推广为整机性能提升比例。主要确认的收益仍是历史合并环节临时分配下降。桌面 GPU 高占用以及用户观察到的总内存翻倍尚未确认解决。

测试页面已关闭，路由注入、可见性模拟和 GC 会话随之销毁；临时浏览器注入脚本已清理。保留离线基准及 JSON、截图供复核。
